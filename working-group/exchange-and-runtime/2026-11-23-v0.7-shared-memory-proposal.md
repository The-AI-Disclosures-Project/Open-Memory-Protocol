# Open Memory Protocol v0.7 proposal: shared memory

**Proposal, 2026-11-23.** Vasilije Markovic (Cognee). Not discussed with the working group. Follows the 2026-11-12 call. It proposes two additions to [editors' draft v0.6](../../SPEC.md): permission fields on the memory object, and a small git-like set of functions for memory that several people and agents share. Everything here sits in the access-controlled profile (U-7); a folder of markdown still conforms without it. MUST and MAY are RFC 2119 keywords and all of them are proposals.

## 1. Model

| Term | Meaning |
|---|---|
| **Space** | A named line of history inside one store, and the unit access is granted on. Named `kind:value`: `agent:…`, `user:…`, `team:…`, `org:…`. Git: a branch |
| **Ladder** | Space kinds from narrow to wide: agent, user, team, org |
| **Head** | The revision of a memory a space currently serves. Two heads for one memory in one space is a conflict |
| **Commit** | A record of a set of revisions entering a space: who, when, why, and the commits before it |

A commit id hashes its parents, message, author, time and the `(identifier, rev, checksum)` of its changes. It does not hash bodies, so erasing content leaves the history verifiable. That is the one structural difference from git.

## 2. Permission on the memory object

Functions bind only the server they run on. After an export the object is all that arrives, so what a receiver must enforce has to be on it. These fields are interchange only and set by the server, never by the agent (U-11).

| Field | Meaning |
|---|---|
| `scope` | Existing field: the space the memory is served in |
| `access.owner` | The principal who decides how the memory is shared |
| `access.promotion` | `{ status, from, by, at }`, with `status` one of `private`, `proposed`, `promoted` |
| `access.acl` | `{ ref, version }`: the space's grant list at the origin, and the version that applied at export |

```json
"scope": ["team:paper"],
"access": {
  "owner": "user:jordan",
  "promotion": { "status": "promoted", "from": "user:jordan", "by": "user:sam", "at": "2026-11-20T10:02:00Z" },
  "acl": { "ref": "team:paper", "version": 7 }
}
```

With `provenance` and `updated_at` these are the five fields the call asked for: author, last updated, scope, promotion status, access control reference.

**Rules.**

1. **Narrow-only.** Imported `scope` and `access` are the exporter's claims. They can restrict where a memory is served and never widen it. An imported memory enters the importer's own space as `private` and reaches a wider space only by a local `promote` or a mapping a local administrator approved. The receiver keeps the exporter's values under `access.imported`. An import into the origin the export came from restores each memory to its space.
2. **Principals do not match by name.** A principal or scope belongs to the export's `origin`. The receiver maps it to one of its own and reports the mapping in the receipt. A matching name or email address is never a mapping.
3. **Derived memories stay narrow.** A derived memory goes no wider than its narrowest input. A link to a memory the reader cannot read is emitted as dangling, with no reference.
4. **Narrowing travels.** A `demote` produces a withdrawal, a record with no content that travels like a tombstone and makes receivers stop serving their copy. A `revoke` raises the grant list's version and receivers apply the higher one.
5. **The checksum covers `scope` and `access`**, so a copy widened in transit is rejected.
6. **Grant lists travel in the manifest**, once per space with a version, not on each memory. A receiver never creates local grants from them on its own.

These fields are a label and a duty on conforming receivers. They do not protect a memory from a store that ignores them.

## 3. Functions

Agent functions are MCP tools. Administration functions are signatures a server MAY expose as MCP tools; where one needs a person's decision, the server asks through MCP elicitation. Identity is the authenticated caller, never an argument. Exact JSON Schemas follow once the shape is agreed.

```ts
// agent
remember(body, { space?, identifier?, supersedes?, ...metadata })  -> { memory, pending }
recall(query, { spaces?, at?, tags?, limit?, cursor? })            -> { results: { memory, space, conflict? }[] }
commit(message, { space?, identifiers? })                          -> Commit
diff(from, to, { identifiers? })                                   -> { changes: { identifier, change, fields? }[] }

// administration
merge(from, into, { identifiers?, dry_run? })                      -> { status, commit?, results, conflicts }
list_conflicts({ space?, kind?, status? })                         -> { conflicts }
grant(space, principal, permission)                                -> Grant
revoke(space, principal, permission)                               -> { revoked }
promote(identifiers, to, { from?, dry_run? })                      -> { status, commit?, results, conflicts }
demote(identifiers, from, { reason? })                             -> { commit, results }
forget(identifier, reason, { rev? })                               -> { tombstone, erased, pending }
```

| Function | Needs | What it does |
|---|---|---|
| `remember` | `write` | Writes a revision to the caller's pending set in a space. `supersedes` names the revisions it replaces |
| `recall` | `read` | This binding's own query call; the protocol still fixes no recall signature (3.6.2). Returns both sides of an unresolved conflict |
| `commit` | `write` | Makes pending writes visible to everyone with `read` on the space. A server MAY commit every write on its own |
| `diff` | `read` | How one space or commit differs from another, as `[old, new]` per changed field |
| `merge` | `read`, `write` | Brings revisions into a space. Never picks a side: where histories diverged it keeps both heads and reports a conflict |
| `list_conflicts` | `read` | The queue of things that need a decision: `concurrent` edits, `contradiction` between memories, unexpected `access`, and a `promotion` awaiting review |
| `grant`, `revoke` | `share` | Give or remove `read`, `write`, `forget` or `share` on a space |
| `promote` | `write` on target | A merge up the ladder with a gate. The server applies its policy first. A caller without `write` on the target gets `pending_review`; the same call by someone who has it approves |
| `demote` | `write` | Takes memories out of a wider space. Nothing is erased and narrower spaces keep them |
| `forget` | `forget` | True deletion. Content is erased from every revision, a tombstone stays and blocks re-import, and no commit is rewritten |

Each step of the ladder has a promotion mode the server declares: `manual` (a person promotes), `review` (the server proposes, a person approves) or `auto` (the server promotes, a person reviews afterwards and uses `demote`).

Conflicts are resolved with the other functions, so there is no resolve function: a `remember` that supersedes every head, or `grant`, `revoke`, `promote`, `demote`. The protocol requires that conflicts are listed. How a server detects or resolves them stays with implementations, as does sync timing.

## 4. The launch demo

```text
Jordan  remember("Section 3 uses the 2025 dataset, n=412")        pending in user:jordan
Jordan  commit("Notes on section 3")
Sam     recall("sample size")                                     nothing; Jordan's space is private
Jordan  promote([claim], "team:paper")                            promoted
Sam     recall("sample size")                                     the claim, from team:paper
Sam     remember("n=398 after exclusions", { identifier: claim, supersedes: [r1], space: "team:paper" }); commit
Jordan  remember("n=412, two sites", { identifier: claim, supersedes: [r1] }); commit; promote
                                                                  conflicted: two heads in team:paper
Either  list_conflicts({ space: "team:paper" })                   both sides
Sam     remember("n=398 after exclusions, two sites", { identifier: claim, supersedes: [r2a, r2b], space: "team:paper" }); commit
Jordan  forget(note, "user_request")                              erased, tombstone kept
```

Exporting `team:paper` to another system lands the memories in the importer's own space there (rule 1) until an administrator approves a mapping. Importing them back restores them to `team:paper`.

## 5. Open questions

- **R-1.** `recall` returns the `space` beside each memory, and U-12 says `scope` must not reach the agent. An agent cannot promote what it cannot place.
- **R-2.** `access.promotion.status` is a status field, and I-14 proposes none is standard. A receiver cannot derive it once the memory has left its store.
- **R-3.** A withdrawal travels and erases nothing. PR #42 keeps reversible deletes local and sends only forgets.
- **R-4.** Under narrow-only a team moving to another product lands everything in one person's space and needs one approved mapping. Proposed: that is the intended cost.
- **R-5.** Whether an agent may hold the administration functions at all, or only a person.
- **R-6.** `forget` needs the `forget` permission in each space and queues the rest. The alternative lets the memory's owner erase it everywhere.
