# Agent Harness Memory Systems

How shipping agent harnesses handle memory today. These range from coding-
focused assistants to general-purpose personal AI agents that operate across
messaging platforms, desktop apps, and CLI. They share a core problem: an agent
works with a user across many sessions, and it needs to remember context,
preferences, and domain-specific knowledge. The approaches vary from flat files
to structured databases to multi-layered architectures, but several patterns
appear independently across implementations.

## Systems surveyed

### Claude Code (Anthropic)

**Storage:** Markdown files in the project directory and user home.

**Memory structure:**
- `CLAUDE.md` at project root: project-level instructions, conventions, and
  context. Checked into version control. Supports nested `CLAUDE.md` files in
  subdirectories for scoped instructions.
- `.claude/` directory: user-specific and project-specific settings.
- User-level memories in `~/.claude/` for preferences that span projects.

**Scope model:** Three tiers: user (global), project (repo-level), directory
(subdirectory-level via nested CLAUDE.md files).

**Lifecycle:** User-created and agent-created. The agent can write memories
via a structured memory system with typed entries (user, feedback, project,
reference). Memories persist as individual markdown files with YAML frontmatter
containing name, description, and type metadata. An index file (MEMORY.md)
provides a navigable table of contents.

**Retrieval:** CLAUDE.md files at and above the working directory are loaded
into context at session start. The memory index (MEMORY.md) is always loaded;
individual memory files are read on demand when relevant.

**User control:** Full. All memory files are human-readable and human-editable
markdown on the local filesystem. Users can read, edit, and delete any memory.

**Portability:** Files are plain markdown. They can be copied, version-
controlled, and shared. No formal export/import mechanism, but the format is
simple enough that manual transfer works.

**Context injection:** File contents are injected into the system prompt at
session start. The agent reads additional memory files during the session when
it determines they may be relevant.

### Codex (OpenAI)

**Storage:** Markdown file in the project directory.

**Memory structure:** `AGENTS.md` at project root. A single markdown file
containing instructions, conventions, and context for the agent.

**Scope model:** Project-level only. No user-level or directory-level scoping.

**Lifecycle:** Primarily user-created. The file is maintained by the developer
as part of the project, similar to a README or CONTRIBUTING guide.

**Retrieval:** The entire file is loaded into context at session start.

**User control:** Full. Plain text file in the repo.

**Portability:** Plain markdown. Trivially portable.

**Context injection:** Entire file injected into context at session start.

### Goose (Block)

**Storage:** Markdown files in two locations.

**Memory structure:**
- `.goose/memory/` in the project directory for project-level memories.
  Organized by category with tags and scope flags.
- `~/.config/goose/memory/` for global (user-level) memories.

**Scope model:** Two tiers: project and global. Memories carry a scope flag
indicating which level they belong to.

**Lifecycle:** Agent-created via tool calls. The agent writes memories
organized by category.

**Retrieval:** All saved memories are loaded at session start and injected
into every prompt. No selective retrieval or search.

**User control:** Full. Plain text files on the local filesystem.

**Portability:** Plain markdown files. The me.md initiative (David Hamilton,
Block) proposes a user-owned, portable memory file that any agent can read.

**Context injection:** All memories injected into the system prompt. This
approach optimizes for simplicity at the cost of context window space as
memories accumulate.

### Cursor

**Storage:** Markdown files in the project directory.

**Memory structure:** `.cursor/rules` directory containing rule files. Each
file defines instructions, conventions, or context for the agent within a
specific scope.

**Scope model:** Project-level, with file-level scoping via glob patterns
that associate rules with specific files or directories.

**Lifecycle:** Primarily user-created. Some rules are generated by the agent
when instructed.

**Retrieval:** Rules matching the current file context are loaded. Glob
patterns determine which rules apply to which files.

**User control:** Full. Plain text files in the repo.

**Portability:** Plain text. Format is Cursor-specific but human-readable.

### Cline / Roo Code

**Storage:** Markdown files in the project directory.

**Memory structure:** `.clinerules/` directory (Cline) or `.roo/rules/`
directory (Roo Code). Contains instruction files organized by concern.

**Scope model:** Project-level. Roo Code adds mode-specific rules (different
instructions for different agent "modes" like architect, code, review).

**Lifecycle:** User-created, with some agent-written rules.

**Retrieval:** All rule files are loaded into context at session start.

**User control:** Full. Plain text files.

**Portability:** Plain text. Format is specific to each tool but
human-readable.

### Gemini CLI (Google)

**Storage:** Markdown file.

**Memory structure:** `GEMINI.md` at project root, analogous to CLAUDE.md
and AGENTS.md.

**Scope model:** Project-level.

**Lifecycle:** User-created and maintained.

**Retrieval:** Loaded into context at session start.

**User control:** Full. Plain text.

**Portability:** Plain markdown.

### Continue

**Storage:** Configuration files in the project directory.

**Memory structure:** `.continue/` directory containing configuration and
context files. Supports rules and context providers.

**Scope model:** Project-level and user-level (via global configuration).

**Lifecycle:** User-created configuration.

**Retrieval:** Configuration loaded at startup; context providers fetch
additional information on demand.

**User control:** Full. Configuration files in the project.

**Portability:** Configuration format is Continue-specific.

### Aider

**Storage:** Configuration and convention files.

**Memory structure:** `.aider.conf.yml` for configuration. Repository map
(automatic analysis of codebase structure). Convention files for project
context.

**Scope model:** Project-level. No persistent cross-session memory beyond
configuration and git history.

**Lifecycle:** Configuration is user-maintained. The repository map is
generated automatically.

**Retrieval:** Configuration loaded at startup. Repository map consulted for
relevant file selection.

**User control:** Full for configuration. Repository map is auto-generated.

**Portability:** Configuration is YAML. Repository map is ephemeral.

### OpenHands

**Storage:** Event-based logs.

**Memory structure:** Session events stored as structured records. Each event
has a type, timestamp, and content. Events include user messages, agent
actions, observations, and tool results.

**Scope model:** Session-level. No persistent cross-session memory in the
core platform.

**Lifecycle:** Events are appended during a session. Session logs can be
replayed.

**Retrieval:** Full session event history available within a session.
Cross-session retrieval requires external tooling.

**User control:** Session logs are accessible.

**Portability:** Event format can be converted to ATIF (Harbor provides a
converter).

### GitHub Copilot

**Storage:** Configuration files and cloud-side settings.

**Memory structure:**
- Custom instructions via `.github/copilot-instructions.md` (project-level)
- User-level custom instructions in VS Code settings
- Organization-level policies via Copilot Business/Enterprise settings

**Scope model:** Three tiers: user, organization, project.

**Lifecycle:** User and admin-created. The agent does not autonomously
create persistent memories.

**Retrieval:** Instructions loaded based on scope. Project-level instructions
from the current repository take precedence.

**User control:** Full for user-level. Organization-level controlled by admins.

**Portability:** Plain markdown for project instructions. User settings tied
to VS Code/GitHub account.

## General-purpose agent harnesses

The following systems are not limited to coding. They operate across messaging
platforms, desktop apps, and diverse task domains. Their memory architectures
tend to be more sophisticated than coding-focused tools, reflecting the broader
range of knowledge they need to retain.

### OpenClaw

**Storage:** Markdown files plus SQLite database per agent.

**Memory structure:** A layered architecture with distinct persistence surfaces:

- `MEMORY.md`: curated long-term memory (durable facts, decisions). Promoted
  through a biologically-inspired "dreaming" consolidation process.
- `USER.md`: user preferences expressed as imperative directives (not
  observations). Bounded in size, superseded in place.
- `memory/YYYY-MM-DD.md`: daily episodic notes, session summaries.
- `DREAMS.md`: consolidation summaries and dream diary for human review.
- `AGENTS.md` / `SOUL.md`: operating instructions and personality.
- Per-agent SQLite database: memory index with FTS5 search, optional vector
  embeddings (sqlite-vec), chunk provenance metadata, standing intents, session
  history, and dreaming state.

**Scope model:** Agent, user, project, and session scopes. Project scoping
uses Git repository identification: entries carry
`<!-- project: github.com/org/repo -->` annotations, and ranked search boosts
entries matching the active repository. Multi-agent routing supported with
separate memory per agent.

**Lifecycle:** A three-phase "dreaming" consolidation system modeled on sleep
biology runs as a scheduled background sweep:
- Light phase: deduplicates recent signals, stages candidates
- REM phase: builds theme reflections from recent traces
- Deep phase: scores candidates through deterministic gates (minimum score,
  recall count, and unique query thresholds), then consolidates into MEMORY.md

Deep dreaming is the only phase that writes to curated memory. A
`maxPriorEntryLossFraction` limits how much consolidation can remove per sweep.

**Retrieval:** Two-lane recall architecture. Lane 1 (always-on, zero model
calls): bootstrap injection of MEMORY.md/USER.md at session start, ranked
hybrid search (vector + BM25 with exponential recency decay), trigger-based
injection via annotated entries, and project memory blocks. Lane 2
(escalation): a blocking recall sub-agent runs when the message shows recall
intent and Lane 1 produced no strong hit.

**User control:** All memory is plain markdown, editable with any text editor.
CLI tools for search, indexing, promotion, and deletion. Dreaming is toggleable.
Memory writes can require approval. Sessions can be excluded from future
ingestion via admission policies.

**Portability:** Can import memory from Codex, Claude Code, and Hermes.
No formal export standard, but all memory is plain files on disk.

**Context injection:** MEMORY.md and USER.md injected into the system prompt
at session start as a frozen snapshot. Writes during the session persist to
disk immediately but do not alter the current session's prompt (preserving
prefix cache efficiency). Trigger-injected entries and search results are
delivered as hidden context blocks.

**Distinctive features:** Provenance-gated security model where origin classes
(owner, agent, untrusted, system) are stored in SQLite columns the model
cannot write to. Untrusted content is structurally barred from curated memory
and auto-injection. Standing intents provide prospective memory: event-
conditioned actions compiled out of the model into deterministic matching with
fire budgets, cooldowns, and explicit lifecycle states.

### Hermes Agent (Nous Research)

**Storage:** Markdown files plus SQLite database, with a pluggable external
memory provider architecture.

**Memory structure:** Five distinct persistence layers:

1. **Builtin memory** (`~/.hermes/memories/`):
   - `MEMORY.md`: agent's personal notes (environment facts, conventions,
     lessons learned). Bounded at ~800 tokens.
   - `USER.md`: user profile (name, preferences, communication style).
     Bounded at ~500 tokens.
   - Entries delimited by `§` (section sign) characters.
2. **Session database** (SQLite with WAL mode): all conversations with FTS5
   full-text search and CJK support. Compression lineage tracking preserves
   continuity when context is summarized.
3. **Skills** (procedural memory): markdown files in `~/.hermes/skills/`
   following the agentskills.io open standard. The agent can create skills
   autonomously after complex tasks. A curator system auto-transitions skills
   between active, stale, and archived states based on usage.
4. **External memory providers**: plugin architecture with 8 bundled providers
   (Honcho, Mem0, Holographic, and others). One external provider active at a
   time alongside the builtin. The Holographic provider uses algebraic
   reasoning (Holographic Reduced Representations) for compositional retrieval.
5. **Context files**: `.hermes.md`, `AGENTS.md`, `CLAUDE.md`, `.cursorrules`
   loaded from the working directory. Progressive subdirectory discovery during
   sessions.

**Scope model:** User (global via MEMORY.md/USER.md), profile (multiple
isolated Hermes profiles), project (context files), session (SQLite), and
cross-session (via external providers). Multi-platform: operates across CLI,
Telegram, Discord, Slack, WhatsApp, Signal, Email, TUI, and Electron desktop.

**Lifecycle:** Memory writes go through the builtin `memory` tool (add/
replace/remove), optionally gated by a write-approval config. Background
review after each turn may fork the agent to evaluate whether skills or memory
should be updated. The curator runs periodic maintenance on skills. Context
compression creates linked session chains preserving continuity. Pre-compress
hooks let providers extract insights before messages are summarized away.

**Retrieval:** Builtin memory is always in the system prompt (no retrieval
needed). Session search uses FTS5 with deduplication by session lineage.
External providers prefetch on each turn in a background thread. Trivial
prompts (greetings, acknowledgements) skip recall entirely to save round-trips.

**User control:** Extensive. Memory writes can require approval. Providers
are selectable and configurable. Skills can be pinned, edited, or archived.
A visual "journey" timeline shows everything learned. Notification verbosity
is configurable. All memory files are plain markdown.

**Portability:** Reads context files from multiple harness formats (AGENTS.md,
CLAUDE.md, .cursorrules). No formal export standard. Skills follow the
agentskills.io open standard.

**Context injection:** System prompt assembled in a defined order: SOUL.md,
agent identity, context files, frozen memory snapshot with usage percentages,
memory guidance, external provider context, skills index, tool schemas. The
system prompt is byte-stable for the life of a conversation to preserve prompt
caching.

**Distinctive features:** Skills as procedural memory with autonomous creation
and lifecycle management. The self-improvement loop (background review can
patch existing skills) is a form of meta-learning. Eight pluggable memory
providers allow experimentation with different memory architectures without
changing the core agent.

### Pi

**Storage:** JSONL session files plus markdown context files.

**Memory structure:** Pi takes a deliberately minimal approach to persistent
memory, keeping the core small and pushing workflow-specific behavior into
extensions:

- Sessions stored as JSONL files in `~/.pi/agent/sessions/`, organized by
  working directory. Each session is a tree structure supporting branching
  and navigation.
- Context files: loads `AGENTS.md` or `CLAUDE.md` from the working directory
  and parent directories. `AGENTS.override.md` replaces the default for a
  directory. Global instructions at `~/.pi/agent/AGENTS.md`.
- Custom system prompt via `.pi/SYSTEM.md` (project) or
  `~/.pi/agent/SYSTEM.md` (global). Append-only variant via
  `APPEND_SYSTEM.md`.
- No built-in long-term memory extraction or consolidation in the core.
  Memory features are delegated to the extension system.

**Scope model:** Project (context files from working directory and parents),
global (user-level AGENTS.md and settings), and session (per-session JSONL
files). A trust system gates project-local settings and extensions.

**Lifecycle:** Sessions auto-save. Context files are user-maintained.
Compaction handles long conversations: when context exceeds a threshold, Pi
summarizes older messages while preserving recent work. The compaction system
uses a structured summary format tracking goals, progress, key decisions, and
file operations. Branch summarization preserves context when navigating between
branches in the session tree.

**Retrieval:** Context files loaded at session start. Within a session, the
full active branch plus any compaction summaries form the context. No cross-
session search in the core (available via extensions).

**User control:** Full. Sessions exportable to HTML or JSONL. Session picker
with search, rename, and delete. Trust decisions control which project-local
resources are loaded. All context files are plain text.

**Portability:** Sessions exportable to HTML or JSONL. JSONL format is
documented with a public SessionManager API and SDK. The `pi-share-hf` project
publishes sessions to Hugging Face datasets for research.

**Context injection:** System prompt assembled from SOUL/system prompt,
context files, and session state. Compaction summaries injected as structured
blocks containing goals, constraints, progress, key decisions, and file
operation history. Branch summaries injected at navigation points.

**Distinctive features:** The session tree model (branching, navigation,
branch summarization) is unique among the surveyed harnesses. Pi intentionally
omits built-in MCP, sub-agents, permissions, plan mode, and background
processing, instead providing extension points for each. The compaction system
is well-documented at the code level with extension hooks for custom
summarization.

## Convergent patterns

Several patterns appear independently across multiple implementations:

**Markdown as the memory format.** Every harness that persists memory uses
markdown for at least some of its memory surfaces. MEMORY.md, USER.md,
CLAUDE.md, AGENTS.md, SOUL.md: the format is always markdown, often with
structured delimiters or YAML frontmatter for metadata. This convergence is
organic, not coordinated; it reflects that markdown is human-readable,
version-controllable, and LLM-friendly.

**A root file as the entry point.** CLAUDE.md, AGENTS.md, GEMINI.md,
.cursor/rules, .clinerules, .hermes.md: every harness looks for a known file
or directory at the project root. The name differs; the pattern is identical.
Hermes and Pi read multiple formats (AGENTS.md, CLAUDE.md, .cursorrules),
demonstrating that cross-harness context file compatibility is already
emerging organically.

**Project-level as the default scope.** Every system supports project-level
memory. User-level (global) memory is common. Organization or team-level
memory is rare (Copilot Enterprise is the notable exception). The general-
purpose agents (OpenClaw, Hermes) add project scoping via Git repository
identification, automatically associating memories with the codebase they
were created in.

**Full user visibility and editability.** Every harness in this survey stores
memories as human-readable files that users can inspect and modify. This
distinguishes harness-based memory from consumer AI memory (ChatGPT) and
managed cloud services where storage is opaque.

**System prompt injection at session start.** Every system loads core memories
into the system prompt when a session begins. The more sophisticated systems
(OpenClaw, Hermes) freeze the memory snapshot for the session's lifetime to
preserve prefix cache efficiency, persisting mid-session writes to disk
without altering the active prompt.

**Load-everything-at-startup for simple systems; search for complex ones.**
Simpler harnesses (Codex, Cursor, Cline) load all memories at startup.
More sophisticated systems (OpenClaw, Hermes, Claude Code) use selective
retrieval: hybrid search, trigger-based injection, or escalation lanes.
The inflection point appears to be memory store size: once memories exceed
what fits comfortably in the context window, selective retrieval becomes
necessary.

## Divergent choices

**File naming and directory conventions.** Every harness has its own: CLAUDE.md,
AGENTS.md, GEMINI.md, .cursor/rules/, .clinerules/, .goose/memory/,
.hermes.md. There is no shared convention. A user who works with multiple
harnesses maintains multiple memory files with duplicated content. The
cross-format reading in Hermes and Pi (both read AGENTS.md and CLAUDE.md)
is a pragmatic step toward interoperability.

**Memory architecture depth.** The systems span a wide spectrum. At one end,
Codex uses a single markdown file with no retrieval. At the other, OpenClaw
has a five-surface architecture with three-phase dreaming, trigger-based
injection, provenance-gated security, and standing intents. Hermes has five
persistence layers with pluggable external memory providers. The standard
needs to accommodate both ends of this spectrum.

**Agent-authored vs user-authored memory.** Some systems (Codex, Cursor,
Gemini CLI) treat memory files as user-authored documentation the agent
consumes but does not write. Others (Claude Code, Goose) have the agent
create memories autonomously. The most sophisticated systems (OpenClaw,
Hermes) use background consolidation to promote observations into curated
memory through deterministic gates. The authorship model affects provenance:
who is responsible for the accuracy of a memory?

**Scope granularity.** Claude Code supports directory-level scoping (nested
CLAUDE.md files). Cursor supports file-level scoping (glob patterns on rules).
OpenClaw and Hermes support project-level scoping via Git repository
identification. Most others are project-level only.

**Memory structure.** Claude Code structures memories with typed entries
(user, feedback, project, reference) and YAML frontmatter. OpenClaw uses
entry-level annotations for triggers, projects, and importance. Hermes uses
section-sign delimiters with bounded capacity. Most coding-focused agents
use unstructured prose. The structured approach enables selective retrieval;
the unstructured approach is simpler to maintain.

**Consolidation and dreaming.** OpenClaw and Hermes both implement background
memory consolidation (dreaming in OpenClaw, background review in Hermes).
Most other systems have no consolidation: memories accumulate without
curation. The academic evidence (see [Academic Foundations](academic-foundations.md))
supports consolidation for long-lived agents, but it adds significant
implementation complexity.

**Procedural memory.** Hermes stores learned procedures as skills with
lifecycle management (active, stale, archived) and autonomous creation.
OpenClaw's standing intents provide prospective memory (event-conditioned
future actions). Most other systems store only declarative knowledge (facts,
preferences, instructions) without procedures.

## Implications for a standard

The convergence on markdown, root-file entry points, and project-level scoping
suggests that a file-based conformance profile is viable and natural for
harness-based agents. The divergence on naming, structure, and architecture
depth confirms that the standard needs to define a common format that harnesses
can adopt alongside (or in place of) their proprietary conventions.

The fact that Hermes and Pi already read CLAUDE.md and AGENTS.md demonstrates
that cross-harness compatibility is achievable when the format is simple
enough. A standard that defines a common memory file format with structured
metadata (as frontmatter or annotations) could follow the same adoption path:
harnesses read the standard format alongside their native format, giving
users portability without requiring harness authors to abandon their existing
conventions.

The general-purpose agents (OpenClaw, Hermes) demonstrate that memory
architectures will grow in sophistication: dreaming, trigger injection,
provenance gating, procedural memory, and standing intents are features that
simpler systems may adopt over time. A standard should define the minimum
viable memory object without constraining what more sophisticated systems
build on top of it.
